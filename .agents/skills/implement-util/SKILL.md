# implement-util

## 1. 目的

仕様に基づき、堅牢で高品質な Rust のユーティリティ機能を TDD (Test-Driven Development) のプロセスに従って実装する。

実装にあたっては、既存のプロジェクト構成、設計方針、コーディング規約を尊重し、必要最小限の変更で仕様を満たすことを基本方針とする。

## 2. 入力

| 入力 | 必須 | 説明 |
|---|---|---|
| 機能仕様 | 必須 | 実装したい機能の詳細（目的、インターフェース、期待される挙動、エラー条件など） |
| 対象クレート/パス | 必須 | 実装対象となるクレート名、または既存のファイルパス |

## 3. 手順

### STEP 1. 仕様の理解とインターフェース設計

1. 与えられた仕様を詳細に読み解く。
2. プロジェクトの構成を確認する。
    - `Cargo.toml` を確認する。
    - Workspace構成の場合は、メンバークレートと依存関係を確認する。
    - 既存のモジュール構成、公開API、関連テストを確認する。
3. 実装すべき公開インターフェース（関数、構造体、トレイト、列挙型など）を検討し、仕様に沿った設計を行う。
4. エラー型、所有権、ライフタイム、スレッド安全性など、Rust特有の設計上の考慮事項を確認する。
5. 既存の公開APIとの互換性を確認する。
6. 必要に応じて、設計内容や不明点をユーザーに確認する。
7. 実装方針とテスト方針を確定する。

### STEP 2. Gitブランチの作成

1. Gitリポジトリ内であることを確認する。
2. `git status` を実行して現在の作業ツリーの状態を確認する。
3. 現在のブランチを確認する。
4. 以下の命名規則で機能開発用ブランチを作成する。

   ```bash
   git switch -c features/<implement内容>
   ```

5. `<implement内容>` は実装する機能の内容を英語の kebab-case で簡潔に表現する。
    - 例: `features/add-sql-logger`
    - 例: `features/add-file-rotation`
    - 例: `features/fix-error-handling`
6. ブランチ名は仕様と実装内容に対応したものにする。
7. 同名ブランチがすでに存在する場合は、既存ブランチを勝手に使用せず、別名を検討する。
8. 作業ツリーに未コミットの変更がある場合は、その内容を確認する。
    - ユーザーの変更を勝手に破棄、上書き、リセット、stash しない。
    - 既存の変更が今回の作業に影響する場合は、ユーザーに確認する。
    - 安全にブランチを作成できない場合は、作業を中断してユーザーに確認する。
9. ブランチ作成に失敗した場合は、原因を確認し、勝手に別の方法でGitの状態を変更しない。
10. ブランチ作成後、`git branch --show-current` を実行し、作成したブランチに切り替わっていることを確認する。

### STEP 3. テストの作成 (Red)

1. 仕様に基づき、まず失敗するテストを作成する。
2. テストは以下の内容を網羅すること：
    - **正常系**: 仕様通りの入力に対する期待される出力。
    - **境界値**: データの最小値、最大値、空の状態など。
    - **異常系**: 不正な入力やエラーが発生すべきケース。
3. 既存のテスト構成に従い、適切な場所にテストを追加する。
    - 単体テストは原則として対象モジュール内に記述する。
    - 統合テストは `tests/` ディレクトリに配置する。
    - 既存のテスト命名規則がある場合は、それを優先する。
4. **テスト命名規則**: `test_[関数名]_[期待される結果]` の形式とする（例: `test_add_should_be_5`）。
5. 必要に応じて、正常系だけでなくエラー型やエラー内容も検証する。
6. `cargo test` を実行し、テストが意図通りに失敗することを確認する。
7. 失敗理由が未実装の機能によるものであることを確認する。
    - コンパイルエラーやテストコード自体の不備による失敗を、TDDの意図した失敗として扱わない。
    - 既存テストが最初から失敗している場合は、その内容を確認してユーザーに報告する。

### STEP 4. 実装 (Green)

1. テストをパスさせるために、最小限の実装を行う。
2. 既存の設計方針、命名規則、コーディング規約に従う。
3. **エラー処理方針**:
    - `Result` 型を適切に使用する。
    - 必要に応じて `thiserror` 等を用いて明示的なエラー型を定義する。
    - `unwrap()` や `expect()` の安易な使用は禁止する。
    - ただし、テストコードや、論理的に失敗しないことが保証された不変条件の検証など、正当な理由がある場合は使用を許可する。
    - ライブラリコードでは、呼び出し元がエラーを適切に処理できる設計を優先する。
4. 所有権やライフタイムを不必要に複雑化させない。
5. 不要な `unsafe` の使用を禁止する。
6. 仕様にない機能を独断で追加しない。
7. `Cargo.toml` の依存関係を追加・変更する場合は、その必要性を確認する。既存の依存関係で対応できる場合は新たな依存を追加しない。
8. 実装が完了したら、対象クレートの `cargo test` を実行し、作成したテストがすべてパスすることを確認する。

### STEP 5. 品質ガード (Refactor & Check)

1. コードの品質を担保するため、以下のコマンドを実行する。

   ```bash
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets --all-features -- -D warnings
   cargo test --workspace
   ```

2. 各コマンドの目的は以下のとおりとする。
    - `cargo fmt`: Workspace全体のフォーマット確認。
    - `cargo clippy`: Workspace内の全クレート、全ターゲット、全Featureを対象とした静的解析。
    - `cargo test`: Workspace内の全クレートのテスト実行。
3. 品質ガードがエラーを返した場合は、原因を調査して修正する。
4. 修正後は、関連テストと品質ガードを再実行し、すべてパスすることを確認する。
5. 品質ガードの修正によって既存コードに影響が出た場合は、その変更内容を確認する。
6. 環境や依存関係の問題で実行できない場合は、その事実を明確に報告し、成功したものとして扱わない。
7. `cargo fmt --all -- --check` が失敗した場合、フォーマットを適用するには `cargo fmt --all` を実行する。

### STEP 6. 振り返り (Retro)

1. 作業がすべて完了し、品質が担保されたことを確認する。
2. `retro` スキルを呼び出し、実行結果の振り返りを行う。
3. 振り返りでは、以下の観点を考慮する。
    - 仕様に対する実装の妥当性。
    - テストの網羅性。
    - 実装中に発生した問題とその解決方法。
    - 改善できる設計や実装方針。
4. `retro` の結果も必要に応じて完了報告に含める。

### STEP 7. 完了報告

以下の内容を整理してユーザーに報告する。

- 実装した機能の概要。
- 変更・追加したファイル。
- 作成したテストケースの概要。
- テスト実行結果。
- `cargo fmt` の実行結果。
- `cargo clippy` の実行結果。
- 作成したGitブランチ名。
- 未解決の問題や注意事項。
- `retro` の実行結果。

## 4. 判断基準

- 仕様とインターフェースが明確になっているか？
- 実装対象クレートと依存関係が適切に把握されているか？
- 機能開発用のGitブランチが作成されているか？
- TDDに従い、テストが意図した理由で失敗することを確認したか？
- 実装がすべてのテストをパスしているか？
- `cargo fmt` が正常に実行されているか？
- `cargo clippy` が警告・エラーなしで完了しているか？
- Workspace全体のテストがパスしているか？
- 既存機能や公開APIに意図しない影響が発生していないか？

## 5. 完了条件

- 仕様と実装方針が確定している。
- 機能開発用のGitブランチが作成されている。
- TDDに従ってテストが作成されている。
- すべてのテストがパスしている。
- `cargo fmt` を実行済みである。
- `cargo clippy` を通過している。
- Workspace全体のテストがパスしている。
- `retro` スキルが呼び出されている。
- 実装内容と検証結果がユーザーに報告されている。

## 6. 禁止事項

- テストを作成せずに実装を開始すること。
- テストが失敗した原因を確認せずに実装を進めること。
- `unwrap()` や `expect()` を、正当な理由なく使用すること。
- 不要な `unsafe` を使用すること。
- 仕様にない機能を独断で追加すること。
- 品質ガード（fmt, clippy, test）がエラーを返している状態で作業を完了すること。
- ユーザーの未コミット変更を勝手に破棄、上書き、リセット、stash すること。
- ユーザーの許可なく既存ブランチを削除すること。
- 今回の仕様に関係のないコードを不用意に変更すること。
- テストや品質ガードの失敗を隠して完了扱いにすること。
- `retro` を呼び出さずに終了すること。
- ユーザーの許可なく `git commit` や `git push` を実行すること。
